起き上がり（G1）が進まない原因は**床から立ち上がる動作の探索だけ**に絞られた。

鍵は「転倒で試行を終える」設定である。倒れても 60 秒続ける設定では、立位から 0.3 秒で
倒れた後の 59 秒を臥位で過ごし、立位維持の信号が 1/60 に薄まっていた。

## 3. M2（一脳）の実装と実走

設計・実装を三つのパケットに分けて Devin（SWE-2）へ委譲し、指揮官が差分と検証を再実行して取り込んだ。

- `brain/build.py` + `brain/policy.py`: 全規模の神経中核（N=71,618、nnz=7,882,609、c=0.0207）を組み立て、tanh 前の読出しを平均とするガウス方策として包む。状態 (v, I, s) を環境ごとに持ち回る。
- `learning/ppo_window.py`: 切り詰め窓の BPTT による PPO。窓を最小単位に、保存した開始状態から再計算して窓ごとに逆伝播する。**再計算が収集時の軌道を再現することを試験で確認**（窓内リセットを含めて logp が atol 1e-4 で一致）。
- `scripts/train_mono.py`: mono の学習スクリプト。神経活動を §11.2 の MBA1 フレームで配信する（更新ごとに 1 枚）。

## 4. 直したもの（一晩で見つけた不具合）

| 箇所 | 症状 | 原因 |
|---|---|---|
| 姿勢配信 | 学習ループから 192 ステップで 1 枚しか届かない | 同じ身体ステップで GPU コピーを投入してから完了照会していた。read → 送信 → enqueue の順に直した |
| 配信サーバの終了 | 毎回 websockets の Traceback | ハンドラが待機したままサーバの close を観測できていなかった |
| 評価の指標 | 最大骨盤高が 4 回の評価で 4 桁一致 | リセット直後の受動的な転がりを拾っていた。最終骨盤高に替えた |
| 学習ログの統計 | 窓の最終ステップの値だけを記録 | 窓内の平均を取るよう直した |
| 方策の分散 | エントロピーが単調に落ちて床で止まる | 操作の急変の項が探索雑音そのものを罰していた。tanh(μ) で測る形に直し、標準偏差に下限 0.1 を置いた |

## 5. 次の一手

**M1（G1 未達成）**: 報酬の形を五通り試して、いずれも「密な項が釣り合う高さで止まる」形に収束した。
学習処理は健全（clip 率 0.10〜0.15、勾配は全パラメータに到達、骨盤高は単調改善）なので、
残る問題は探索である。PLAN §12.3 に置いた順序で次を試す。

1. 密な高さの係数をさらに上げる（0.15 → 0.4）。跳躍が得にならないかを抜け道試験で先に確かめる。
2. `stand_balance` を転倒で終了させ、立位維持だけを先に学ばせる。いまは倒れた後の 59 秒が臥位なので信号が 1/60 に薄まっている。
3. 模倣学習（PLAN §12.3 の 6）。`mlp_control` に手書きの起き上がり軌道を写してから PPO に入る。

**M2**: 実装は完了し、全規模で 160 万身体ステップを安定走行した。
G2（5×10^8）は 256 環境で 75 時間なので、M1 の決着を待ってから始めるのが妥当である。
先に §7 のハイパーパラメータ探索（`mono` の `stand_balance`、各 5×10^7）を回す手もある。
